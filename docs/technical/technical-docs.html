Architecture Specification

FADO AssetFlowPro là hệ thống quản lý vòng đời tài sản doanh nghiệp, xây dựng trên Next.js 13.5 App Router. Toàn bộ frontend, backend API và business logic nằm trong một monorepo duy nhất.

App Router Structure

Mỗi feature là một thư mục riêng dưới src/app/, gồm page, components cục bộ, và API routes.

src/
├── app/
│   ├── (auth)/                   # route group — không có segment
│   │   └── login/page.tsx
│   ├── dashboard/
│   │   └── page.tsx              # /dashboard
│   ├── assets/
│   │   ├── page.tsx              # /assets — danh sách
│   │   ├── components/           # component cục bộ của feature
│   │   └── [id]/page.tsx         # /assets/:id — chi tiết
│   └── api/
│       ├── assets/
│       │   ├── route.ts          # GET list, POST create
│       │   └── [id]/route.ts     # GET, PUT, DELETE item
│       ├── auth/
│       │   └── login/route.ts
│       └── public/               # không cần auth
├── components/               # shared UI components
│   ├── ui/                   # primitives: Button, Input, Badge…
│   └── AppLayout.tsx         # wrapper chính (Sidebar + Topbar)
├── hooks/                    # useUserPermissions, useRealtimeData…
├── context/                  # NotificationContext, AuthContext
└── lib/
    ├── db.ts                 # pg Pool + helper functions
    ├── modules.ts            # định nghĩa module + action (RBAC)
    ├── permissions.ts        # canAccess, hasModulePermission
    ├── api-permissions.ts    # middleware check quyền cho API
    ├── zimbra/               # SOAP client
    └── services/             # *Service.ts — business logic

Module Boundaries

📄 Page Layer
app/[feature]/page.tsx — Render UI, gọi API, không chứa SQL. Luôn wrap trong <AppLayout>.
🔌 API Layer
app/api/[feature]/route.ts — Nhận request, check auth/permission, gọi service, trả JSON.
⚙️ Service Layer
lib/services/[name]Service.ts — Business logic, SQL query. Hàm thuần, không dùng NextRequest/Response.
🗄️ DB Layer
lib/db.ts — Pool kết nối duy nhất, helper functions. Không tạo Pool mới ở bất kỳ chỗ nào.
💡
Quy tắc import chiều dọc
Page → API (qua fetch) → Service → DB. Không import ngược. Service không được import từ app/. DB helper không được import từ lib/services/.

Database Guide

Connection — pg Pool

Toàn bộ truy cập DB đi qua một Pool duy nhất khởi tạo trong src/lib/db.ts. Không bao giờ tạo new Pool() ở file khác.

// src/lib/db.ts — cấu hình Pool
import { Pool } from 'pg';

const pool = new Pool({
  connectionString: process.env.DATABASE_URL,
  max: parseInt(process.env.PG_POOL_MAX ?? '30'),
  ssl: process.env.PGSSL === 'true' ? { rejectUnauthorized: true } : false,
});

Helper Functions

Bốn helper chính — sử dụng thay vì pool.query() trực tiếp để có type-safety và error logging đồng nhất.

query<T>(sql, params?) → Promise<T[]>
Trả mảng rows. Dùng cho SELECT nhiều kết quả.
const users = await query<User>(
  `SELECT id, "fullName", email FROM users WHERE "companyId" = $1`,
  [companyId]
);
queryOne<T>(sql, params?) → Promise<T | null>
Trả một row hoặc null. Dùng cho lookup theo ID / điều kiện unique.
const user = await queryOne<User>(
  `SELECT * FROM users WHERE id = $1`,
  [userId]
);
if (!user) throw new Error('Không tìm thấy người dùng');
execute(sql, params?) → Promise<QueryResult>
Cho INSERT / UPDATE / DELETE — không cần lấy rows. Trả QueryResult (có .rowCount).
await execute(
  `UPDATE assets SET status = $1, "updatedAt" = NOW() WHERE id = $2`,
  ['inactive', assetId]
);
withTransaction<T>(fn) → Promise<T>
Bao bọc nhiều thao tác trong một transaction. Tự động ROLLBACK nếu có lỗi.
const result = await withTransaction(async (client) => {
  await client.query(`INSERT INTO asset_logs ...`, [...]);
  await client.query(`UPDATE assets SET ...`, [...]);
  return { success: true };
});

buildInsert & buildUpdateById

Hai helper sinh SQL tự động, tự quote camelCase columns. Không cần viết INSERT thủ công.

// INSERT
const { sql, values } = buildInsert('assets', {
  id: 'ast_abc123',
  assetName: 'Laptop Dell XPS',
  serialNumber: 'SN-001',
  companyId: 'cmp_xyz',
  createdAt: new Date(),
});
await execute(sql, values);
// → INSERT INTO assets ("id","assetName","serialNumber","companyId","createdAt")
//   VALUES ($1,$2,$3,$4,$5)

// UPDATE by ID
const { sql: uSql, values: uVals } = buildUpdateById('assets', assetId, {
  assetName: 'Laptop Dell XPS 15',
  updatedAt: new Date(),
});
await execute(uSql, uVals);
// → UPDATE assets SET "assetName"=$1,"updatedAt"=$2 WHERE id=$3

⚠️
DATE column gotcha
pg mặc định parse cột DATE thành JavaScript Date object → bị offset timezone. Fix: db.ts đã cấu hình pg.types.setTypeParser(1082, val => val) để trả chuỗi YYYY-MM-DD nguyên bản. Không override lại.

Auth Check Pattern

Mọi protected route đều đọc x-current-user-id header (được middleware Next.js inject từ cookie). Nếu không có → 401.

// Chuẩn xác auth — đầu mỗi API handler
import { NextRequest, NextResponse } from 'next/server';

export async function GET(request: NextRequest) {
  const userId = request.headers.get('x-current-user-id');
  if (!userId) {
    return NextResponse.json({ error: 'Chưa đăng nhập' }, { status: 401 });
  }
  // ... tiếp tục
}

Permission Check Pattern

import { checkPermission } from '@/lib/api-permissions';

export async function POST(request: NextRequest) {
  const userId = request.headers.get('x-current-user-id');
  if (!userId) return NextResponse.json({ error: 'Unauthorized' }, { status: 401 });

  const hasPermission = await checkPermission(request, 'assets', 'create');
  if (!hasPermission) {
    return NextResponse.json({ error: 'Không có quyền' }, { status: 403 });
  }
  // ... xử lý
}

GET Collection — Ví dụ đầy đủ

// app/api/assets/route.ts
import { NextRequest, NextResponse } from 'next/server';
import { getAssets } from '@/lib/services/assetService';

export async function GET(request: NextRequest) {
  try {
    const userId = request.headers.get('x-current-user-id');
    if (!userId) return NextResponse.json({ error: 'Chưa đăng nhập' }, { status: 401 });

    const { searchParams } = new URL(request.url);
    const page    = parseInt(searchParams.get('page') ?? '1');
    const limit   = parseInt(searchParams.get('limit') ?? '20');
    const search  = searchParams.get('search') ?? '';

    const { data, total } = await getAssets({ page, limit, search, userId });

    return NextResponse.json({ success: true, data, total, page, limit });
  } catch (err) {
    console.error('GET /api/assets error:', err);
    return NextResponse.json({ error: 'Lỗi server' }, { status: 500 });
  }
}

GET by ID

// app/api/assets/[id]/route.ts
export async function GET(
  request: NextRequest,
  { params }: { params: { id: string } }
) {
  try {
    const userId = request.headers.get('x-current-user-id');
    if (!userId) return NextResponse.json({ error: 'Unauthorized' }, { status: 401 });

    const asset = await getAssetById(params.id);
    if (!asset) return NextResponse.json({ error: 'Không tìm thấy' }, { status: 404 });

    return NextResponse.json({ success: true, data: asset });
  } catch (err) {
    console.error(`GET /api/assets/${params.id} error:`, err);
    return NextResponse.json({ error: 'Lỗi server' }, { status: 500 });
  }
}

POST Create

export async function POST(request: NextRequest) {
  try {
    const userId = request.headers.get('x-current-user-id');
    if (!userId) return NextResponse.json({ error: 'Unauthorized' }, { status: 401 });

    const body = await request.json();
    const { assetName, serialNumber, categoryId } = body;

    if (!assetName || !serialNumber) {
      return NextResponse.json({ error: 'Thiếu thông tin bắt buộc' }, { status: 400 });
    }

    const asset = await createAsset({ assetName, serialNumber, categoryId, createdBy: userId });
    return NextResponse.json({ success: true, data: asset }, { status: 201 });
  } catch (err) {
    console.error('POST /api/assets error:', err);
    return NextResponse.json({ error: 'Lỗi server' }, { status: 500 });
  }
}

PUT Update & DELETE

export async function PUT(
  request: NextRequest,
  { params }: { params: { id: string } }
) {
  try {
    const userId = request.headers.get('x-current-user-id');
    if (!userId) return NextResponse.json({ error: 'Unauthorized' }, { status: 401 });

    const body = await request.json();
    const updated = await updateAsset(params.id, body);
    return NextResponse.json({ success: true, data: updated });
  } catch (err) {
    console.error(`PUT /api/assets/${params.id} error:`, err);
    return NextResponse.json({ error: 'Lỗi server' }, { status: 500 });
  }
}

export async function DELETE(
  request: NextRequest,
  { params }: { params: { id: string } }
) {
  try {
    const userId = request.headers.get('x-current-user-id');
    if (!userId) return NextResponse.json({ error: 'Unauthorized' }, { status: 401 });

    await deleteAsset(params.id);
    return NextResponse.json({ success: true, message: 'Đã xóa' });
  } catch (err) {
    console.error(`DELETE /api/assets/${params.id} error:`, err);
    return NextResponse.json({ error: 'Lỗi server' }, { status: 500 });
  }
}

Migration Guide

Quy trình bắt buộc — Mỗi cột mới = 1 migration

1
Xác định số thứ tự tiếp theo
Kiểm tra thư mục migrations/, lấy số lớn nhất + 1. Ví dụ: có 154_... → tạo 155_....
2
Tạo file SQL với tên chuẩn
Format: NNN_description_snake_case.sql. Ví dụ: 155_add_telegram_id_to_users.sql.
3
Viết SQL dùng IF NOT EXISTS
Đảm bảo migration idempotent — chạy lại không lỗi.
4
Chạy migration trên DB dev
Chạy bằng psql hoặc run-migrations.js trước khi test.

Template migration chuẩn

-- Migration 155: Thêm telegram_id vào bảng users
ALTER TABLE users
  ADD COLUMN IF NOT EXISTS telegram_id   TEXT    UNIQUE,
  ADD COLUMN IF NOT EXISTS telegram_name  TEXT,
  ADD COLUMN IF NOT EXISTS telegram_linked_at TIMESTAMPTZ;

-- Index nếu cần
CREATE UNIQUE INDEX IF NOT EXISTS idx_users_telegram_id
  ON users(telegram_id) WHERE telegram_id IS NOT NULL;

Tạo bảng mới

-- Migration 156: Tạo bảng user_signatures
CREATE TABLE IF NOT EXISTS user_signatures (
  id            TEXT PRIMARY KEY,
  "userId"      TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  template_id   TEXT NOT NULL,
  html_content  TEXT,
  is_active     BOOLEAN DEFAULT TRUE,
  created_at    TIMESTAMPTZ DEFAULT NOW(),
  updated_at    TIMESTAMPTZ DEFAULT NOW()
);

Migration Runner

File run-migrations.js ở root theo dõi migration đã chạy trong bảng schema_migrations. Tự động chạy khi app khởi động (startup script).

// Bảng tracking
CREATE TABLE IF NOT EXISTS schema_migrations (
  filename   TEXT PRIMARY KEY,
  run_at     TIMESTAMPTZ DEFAULT NOW()
);
// Runner đọc thư mục migrations/, sắp xếp numeric,
// bỏ qua file đã có trong schema_migrations.

reconcile.sql

File migrations/reconcile.sql là script fix thủ công khi có migration trùng số thứ tự hoặc cần idempotent re-run toàn bộ schema. Chạy một lần khi setup DB mới trên server sạch.

🔴
Migration số thứ tự trùng — vấn đề đã biết
Hiện có hai file mang số 008, 009, 012 trong thư mục migrations. Thứ tự chạy trên DB mới là không xác định. Khi init DB lần đầu, dùng reconcile.sql để đảm bảo schema đúng.

Security Notes & Known Tech Debt

Phần này ghi lại các vấn đề bảo mật đã biết trong codebase hiện tại. Không nhân rộng các pattern này — ưu tiên fix khi làm feature mới liên quan.

🔴
CRITICAL: x-user-permissions header có thể bị giả mạo
api-permissions.checkPermission() hiện đọc quyền từ header x-user-permissions do client tự gửi. Bất kỳ ai cũng có thể gửi header này với quyền tùy ý. Đây là placeholder chưa có auth server-side thật. Khi viết API mới, đừng coi cơ chế này là đủ an toàn. Cần thay bằng token/session verify phía server.
🟠
Hai hệ auth song song — mâu thuẫn
Luồng đúng: POST /api/auth/login → DB lookup + bcrypt.compare() → session cookie.
Legacy: src/lib/authStore.ts dùng MOCK_USERS so sánh password plaintext phía client.
Cần gỡ phần mock và thống nhất về luồng bcrypt. Không viết code mới dùng authStore.
🟡
Migration trùng số thứ tự
Tồn tại hai file mang số 008, 009, 012 trong thư mục migrations/. Thứ tự chạy khi init DB mới là không xác định (phụ thuộc filesystem sort). Rủi ro: schema không nhất quán trên server mới. Cần rename và consolidate.
🟡
RLS Policy không có giá trị bảo mật
Một số migration cũ tạo RLS policy với USING(true) — nghĩa là cho phép tất cả. Policy này không hạn chế gì và cho cảm giác an toàn giả. Access control thực sự phải thực hiện ở application layer (API route + service).

Hướng fix ưu tiên

Vấn đềĐộ ưu tiênHướng giải quyết
Permission header spoofable CRITICAL Verify quyền từ DB dựa trên userId từ session cookie — không đọc từ client header
Dual auth system HIGH Xóa authStore.ts và MOCK_USERS. Tất cả login đi qua /api/auth/login
Migration số trùng MEDIUM Rename file bị trùng, cập nhật schema_migrations tracking table
RLS allow-all LOW Xóa RLS policy hoặc viết lại meaningful. Không tạo thêm USING(true).

Best Practices hiện tại cần tuân thủ

🔒 Không hardcode credentials
Mọi key, password, token phải qua process.env. Không commit .env vào repo.
🚫 Không log dữ liệu nhạy cảm
Không console.log(password), token, hoặc PII. API error log chỉ ghi message kỹ thuật.
🛡️ Validate input tại API layer
Kiểm tra các field bắt buộc, type, length trước khi truyền xuống service. Trả 400 khi thiếu dữ liệu.
🔑 Parameterized queries
Luôn dùng $1, $2... placeholder. Không nối string SQL trực tiếp → ngăn SQL injection.
